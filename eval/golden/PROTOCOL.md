# Golden set protocol

How the 43 cases in `qa.jsonl` were built, why each defence works, and what bias
survives all of them. Read this before quoting any number the evaluation prints.

## The problem this document exists to address

A candidate who writes both the corpus and the questions has measured nothing.
The questions inherit the corpus's vocabulary, the retriever gets tuned until
they pass, and the resulting table is a picture of the author's own hand. Anchor
attacks that in four independent ways and then states the residual bias out loud
instead of hiding it.

Every case carries a `provenance` field, so a reviewer can see which tier
produced it, and `report.py` breaks every metric out by provenance so no tier can
hide inside an average.

| tier | `provenance` | n | how it was produced |
| --- | --- | ---: | --- |
| mechanical factual | `mechanical` | 24 | generated by a program from raw corpus text |
| unanswerable | `entity_substituted` | 10 | mechanical case, subject swapped for an entity proven absent |
| multi-hop | `authored` | 5 | hand-written, two documents each |
| arithmetic | `authored` | 4 | hand-written, answerable from `corpus/metrics.csv` |

---

## Defence 1 — the questions are generated by a program, not written by hand

24 of 43 cases come out of `scripts/build_golden.py`. That script reads corpus
text and nothing else. It has no import of, and no knowledge of, the chunker,
the embedder, the retriever, the abstain gate or the prompts, so it cannot be
tuned towards them even by accident. The forbidden set is:

```
anchor.retrieval   anchor.embed   anchor.store
anchor.llm         anchor.judge   anchor.service
```

`tests/test_golden_integrity.py` enforces that twice: statically, by parsing the
builder's AST and asserting its only `anchor` imports are `anchor.textutil` and
`anchor.ingest`; and dynamically, by importing the builder in a clean subprocess
and asserting no forbidden module appears in `sys.modules`. The subprocess
matters — a static check alone would miss a forbidden module arriving
transitively, and an in-process check could pass by accident because some other
test had already imported the retriever.

The pipeline is five deterministic steps. There is no randomness anywhere in it.

**(a) Typed fact extraction.** Each document is split into `##` sections, each
section into sentences, and each sentence is tested against six extractors in a
fixed priority order: `latency_ms`, `percent`, `money`, `duration`,
`count_threshold`, `identifier`. The first extractor that matches wins, and
within it the first match wins. Priority is what makes `850 ms` a latency rather
than a count, and `$4,200` money rather than a bare number.

**(b) Stem construction.** The matched span becomes the answer. The rest of the
sentence — cut at the nearest colon or semicolon so a compound sentence cannot
drag its unrelated half along — plus the section heading becomes the raw stem.
The section leaf is used, deliberately *not* the full heading path including the
document title: putting "Meridian Data Retention Policy" into every question
would hand the retriever the answer document for free and quietly inflate recall.

**(c) Lexical divergence.** A fixed 75-entry `SYNONYM` map rewrites the stem in
one pass over the original tokens, so no replacement can feed another:
`retained → kept`, `window → period`, `request → call`, `threshold → limit`,
`escalate → raise`, `endpoint → route`, `tenant → customer`, and so on. Only
purely alphabetic tokens are rewritten, which is what keeps `SEV-2`,
`/v1/generate`, `Retry-After` and `tnt-0471` intact. The clause's leading
auxiliary is then fronted — but only when it is the clause's *first* verb, so
"a tenant index that has not been rebuilt" is never mangled into "has a tenant
index that not been rebuilt" — and the result is rendered through a template
keyed by fact type ("how long …", "what percentage …", "which identifier …").

**(d) The divergence cap.** A case is DISCARDED unless

```
jaccard(content_tokens(question), content_tokens(source_sentence)) <= 0.5
```

The achieved overlap is stored on every case as `stem_overlap`, and its mean and
max are printed by `make golden` and in the caption of the README table. The
single biggest bias in the set is therefore itself a reported metric rather than
a footnote. `tests/test_golden_integrity.py` recomputes `stem_overlap` from the
question and the gold sentence and asserts the stored value was not simply
written down.

**(e) Labels.** `gold = [{doc_id, answer_span}]` where `answer_span` is the
verbatim source sentence. `answer_aliases` is the target span plus number-word
variants (`90 days` / `ninety days`) and a comma-free variant (`5,000 requests` /
`5000 requests`).

Selection down to exactly 24 is round-robin across documents in `doc_id` order,
and within each document the six fact types are interleaved. That is why the
committed set is four cases per document and spans all six extractors, rather
than being dominated by whichever document happens to contain the most numbers.

**The artifact.** `make golden` regenerates `qa.jsonl`, and the integrity test
asserts the committed file is byte-identical to a fresh regeneration. CI runs the
builder and then `git diff --exit-code`. That is the thing that proves no
question was ever quietly retuned to make a score go up — not a promise, a diff.

## Defence 2 — the unanswerable slice is proven, not asserted

10 of 43 cases are provably unanswerable. Each one is a mechanical case whose
subject entity has been swapped for one drawn from a fixed
`OUT_OF_CORPUS_ENTITIES` list — the Helios queue, the Zurich region, the Nimbus
scheduler, the Quillon catalogue, and so on. The builder **asserts** that the
normalised marker token occurs zero times anywhere in the normalised corpus and
discards the case otherwise, so unanswerability is a checked property of the
corpus rather than the author's opinion. The integrity test re-checks it against
the corpus files directly.

The predicate is left untouched, so the questions stay plausible and on-domain.
"How long must the Saffron pipeline be confirmed within?" is a question a real
user could ask on a bad day; it is not nonsense, and that is exactly what makes
refusing it a real test rather than a nonsense-detector. These cases have
`gold = []`, `answer_aliases = []` and
`expected_answer_type = refused_no_evidence`, and they drive the three rates the
runner reports: `refusal_rate_unanswerable`, `fabrication_rate_unanswerable`
(answered with at least one citation on an unanswerable question) and
`false_refusal_rate_answerable`.

### The limit of this defence, and it is a large one

**The slice proves the questions are unanswerable. It does not prove the system
detects that they are.** Those are different claims and this document used to
run them together.

The control experiment: for each of the 10 entity-substituted cases, put a real
in-corpus phrase back in place of the fabricated entity — making the question
answerable-shaped while changing nothing else — and re-run the whole pipeline.
As shipped the system refuses 7 of 10. The controls refuse 6/10 ("the batch
pipeline"), 7/10 ("the embedding cache"), 5/10 ("the Meridian gateway"), 6/10
("the request logs") and 7/10 ("the on-call lead"). In 5 of the 10 cases the
gate's `lexical_overlap` is byte-identical in both conditions.

So the fabricated entity contributes essentially nothing to the refusal
decision. What the system is responding to is the *shape* of these questions —
a mangled mechanical template whose overlap with every chunk falls under
`gate.min_lexical_overlap` — and not to the absence of their subject from the
corpus. The discrimination signal (refusal on the unanswerable slice minus
refusal on the matched control) is about **0.1 at n=10**, which is
indistinguishable from zero.

`refusal_rate_unanswerable` is therefore best read as: *one measurement — does
this question clear the overlap threshold — repeated ten times.* It is a real
measurement of the guardrail. It is not evidence that this system knows when it
does not know, and the README no longer says that it is.

What would fix it rather than document it: emit a paired `answerable_control`
case for every entity-substituted case and report the **difference** of the two
refusal rates as the headline number; and make unanswerability detectable in
principle by requiring the substituted entity to be the grammatical subject of
the predicate the answer depends on, so that an entity-aware system can win
where a lexical-overlap gate cannot. Neither is implemented. Until they are,
this section is the honest statement of what the 0.700 means.

## Defence 3 — labels are spans, resolved at eval time

`gold` NEVER references a chunk id. `eval/cases.resolve_gold_chunks` normalises
the span and each chunk of that `doc_id`, and returns every chunk whose
normalised text contains the span, raising `EvalError` naming the case and the
span when a label resolves to zero chunks.

This is the reason the chunking half of the ablation is legitimate instead of
self-fulfilling. If gold were a list of chunk ids, re-chunking at 256 or 1024
tokens would invalidate every label, and any honest comparison across chunk
sizes would be impossible — you would be measuring the labels, not the chunker.
Because gold is a span, changing chunk size or overlap cannot invalidate a
single label. The same 43 questions mean the same thing in all six chunk
configurations.

The integrity test asserts up front that every span really is a verbatim
normalised substring of the document it claims, so a broken label fails fast in
a one-second test rather than halfway through an eval run.

## Defence 4 — the authored tier is quarantined and flagged

9 of 43 cases were written by hand, and the repository says so everywhere they
appear. No mechanical generator produces a genuine two-document join or a
computation over a CSV, so these could not have been generated:

* **5 multi-hop**, each with gold spans from two different documents — for
  example, why the April stall could not be reconstructed needs both the
  postmortem's statement that the logs were gone and the retention policy's
  90-day window that explains why.
* **4 arithmetic**, each answerable from `corpus/metrics.csv` with
  `expected_tool` set to `calculator` or `lookup_metric`.

They live in `authored_seed.jsonl` and are merged in by the builder, which
re-verifies that every authored gold span is a verbatim normalised substring of
its document and raises a clear error naming the case if not. `report.py` breaks
every metric out by provenance, so a reviewer can see at a glance which numbers
depend on questions the author wrote.

## The human labels behind judge validation

`human_labels.jsonl` holds 30 frozen `(question, answer, evidence[])` triples:
12 faithful answers copied from corpus sentences, 9 partial answers where
exactly one clause is unsupported, 9 fabricated answers asserting facts absent
from — or contradicting — the evidence. Each carries a label in
`{grounded, partial, ungrounded}` and a one-line rationale. They span all six
documents.

The protocol, stated plainly:

* **One annotator.** The author. There is no second annotator and therefore no
  inter-annotator agreement figure.
* **Labels were written before any judge output was seen.** The triples were
  constructed by taking a corpus sentence and deciding in advance what kind of
  answer to write against it — faithful, one-clause-unsupported, or fabricated.
  The label is a property of how the row was constructed, not a reaction to what
  the judge said.
* **The text is frozen in the file.** Judge validation therefore needs no live
  run, costs nothing, and does not drift when retrieval changes.
* **Cohen's kappa here measures judge-vs-author agreement, NOT judge-vs-truth.**
  A high kappa means the judge reproduces one person's labelling of 30 rows. It
  is evidence that the judge is not arbitrary. It is not evidence that the judge
  is correct.

That last point is the whole reason `make judge-check` exists. An unvalidated
judge is not evidence at all — it is a number with a confident name. A judge
validated against one annotator is weak evidence, honestly described. The
repository ships the weak evidence and the description rather than the confident
name.

## Residual bias — what survives all four defences

1. **The corpus is synthetic and self-written**, so absolute scores say nothing
   about performance on real customer documents.
2. **24 questions are machine-derived from the same corpus** and constrained to
   at most 0.5 lexical overlap with their source sentence — the mean achieved
   overlap is printed — so absolute recall is still optimistic, and only the
   RELATIVE deltas in the ablation table should be trusted.
3. **9 questions were written by the author** and are flagged as such in every
   table.
4. **n = 43**, so every rate is a smoke-grade signal and no difference of a few
   points is real.
5. **The default profile is a hashing embedder and an extractive stub**, so the
   numbers measure the PIPELINE — retrieval, span resolution, gating, refusal,
   citation — and not model quality.
6. **The judge is validated against one annotator's labels**, so Cohen's kappa is
   agreement with the author, not with truth, and an unvalidated judge would not
   be evidence at all.

## Regenerating

```bash
make golden      # rewrites eval/golden/qa.jsonl and prints the composition table
make test        # asserts the committed file is byte-identical to a fresh build
```

If you edit the corpus, regenerate and commit both. If the builder cannot find
24 surviving mechanical cases it fails loudly and tells you to add facts to the
corpus. Never relax the 0.5 cap to make the count work — the cap is the
measurement.
